# 进销存接入 Zhiyu Memory 方案

完成级别：已评估、已规划。2026年10月22日。

目标是让工作助理和数字大脑长期找得到老板确认过的规则，接得上未完成任务，并能说明依据。建议采用独立记忆服务，通过进销存后端接入。账务、库存、收付款及执行权限仍以进销存原业务处理器和当前数据为准。

本次读取了上游说明、协议、项目装配和来源适配源码，以及当前项目的对话入口、纠错审核、知识维护和数据库事件代码。没有安装服务、迁移数据库、导入真实资料或执行模型调用。上游接口联调和性能验收尚未进行。

## 当前项目可复用的接缝

以下路径位于`tools/production-stage-20261022`，用于定位实现；其中存在尚未发布的改动，施工时必须以重新下载的生产版本为基线。

| 接缝 | 当前实现及证据 | 接入用途 |
| --- | --- | --- |
| 工作助理入口 | `server/src/application.js`中的`/api/assistant/ask`调用`assistant-chat.ask` | 在本地处理与外部问答之间加载经核验的记忆；不能只改personal-assistant而遗漏总入口 |
| 工作问答路由 | `server/src/assistant-chat.js`的`ask`、`eligible`和工作范围判断 | 保留岗位权限、实时账目和已有固定问答优先级，避免连续补充话被误认成个人生活话题 |
| 对话状态 | `server/src/assistant-context.js`的`resolve/create`；`web/assistant.js`中的`conversationContext` | 现有主要状态由浏览器在请求中传回，原版本有30分钟条件；需增加服务端任务记录才能跨刷新和重启恢复 |
| 电子屏 | `server/src/assistant-screen.js`生成带公告ID、revision的操作草稿 | 保存任务对象和草稿；实际发布继续经过原公告接口和版本校验 |
| 教助理说法 | `server/src/assistant-phrases.js`的`save/resolve` | 已有稳定说法映射，但目标类型有限且以文本包含匹配；作为来源，不能把所有句子都映射为操作 |
| 纠错审核 | `server/src/assistant-feedback.js`的`submit/review` | 区分“已处理”与“已生效”；仅经核对并生效的教学内容进入知识候选。实时账目纠错不能变成固定答案 |
| 业务知识 | `server/src/employee-knowledge.js`的`save/remove` | 已有版本、适用范围、有效日期和停用；可提供来源正文与生命周期事件 |
| 账务规则 | `server/src/store-accounting-model.js/.json` | 作为规则说明来源，逐条确认版本、日期、例外和实际实现状态；不能把计划功能描述成已可执行 |
| 事件事务 | `server/src/capacity/postgres.js`的`transaction` | 已在业务事务中写入`erp_outbox`，可复用持久化事件模式 |
| 当前事件消费者 | `server/src/capacity/events.js` | 目前通过pg_notify后即标sent；不能直接把该sent当作记忆送达。记忆同步需要独立投递状态与游标 |

连续对话的新版本已有本地9项测试通过，但尚未发布；这不代表长期记忆服务已经接通，也不代表完整HTTP入口已完成多轮验收。

## 记忆分工

| 内容 | 保存位置和使用方式 | 生命周期 |
| --- | --- | --- |
| 老板确认的经营规则、操作习惯 | 版本化来源，经既定审核后进入长期知识 | 保留历史；按规则复查，改版、撤销或到期后旧知识不能继续用 |
| 当前办理对象、草稿、已确定要求、缺项 | 进销存自己的服务端任务表 | 未完成时可恢复；完成后归档，不自动重复执行 |
| 原始聊天、纠错过程、执行回执 | 原始记录和审计，按需提炼经验 | 不直接当作已审核规则或当前业务结果 |
| 余额、库存、到账状态、当笔酬金 | 原业务库实时查询 | 每次按当前权限取数，历史记忆不能替代当前状态 |

长期记忆不是把所有记录永远拼进提示词。任务开始时只加载相关、有效且当前用户可读的条目，保留来源、适用条件和版本。

## 接入路线

建议使用标准R/K/U接口，独立Node服务与独立PostgreSQL数据库。同一服务器上只绑定回环地址，由进销存后端调用；工作助理与数字大脑使用同一套记忆客户端和来源核验。

上游已提供`MEMORY_SERVICE_STANDARD_PROJECTS_FILE`，可登记受信模块并导出`createStandardProject`。为进销存实现自己的来源、成员授权和业务策略，复用标准知识内核与PostgreSQL存储。默认启动仍检查示例表，正式部署需要处理其启动检查与初始化依赖，不能把默认demo启动成功当作门店接通。

不选择仅提供`/v1/project/call`的installed模式作为第一版：该模式不会自动获得标准召回、提案和受控交付能力。以后若迁移已有复杂业务记忆，需另行定义该模式的操作契约。

调用顺序：

1. 进销存认证当前用户，恢复其当前任务，判断继续前文还是明确换题。
2. 按任务检索记忆；要交给模型时走prepare/dispatch及登记消费者，不私自转发展示用Pack。
3. 在进销存网关重新核对来源版本、当前角色与业务实现状态。
4. 结合实时查询形成回答或操作草稿，说明依据、缺项和未完成原因。
5. 经原操作确认与权限检查后，由原处理器执行并保存真实业务回执。
6. 将教学、规则修订或有价值的复盘通过持久化任务同步到记忆服务。

数字大脑与工作助理的记忆入口应共用；支付、库存、销售处理器无需整体重写。

## 第一阶段的两个场景

### 电子屏教学与任务延续

来源为老板确认的操作偏好、已核实纠错与公告原单版本。任务记录至少含`tenantId/branchId/userId/taskId/topic/targetId/targetRevision/draft/requirements/missingFields/status/lastOperationReceipt`。

“再短一点”“他们看到就明白了”“用刚才那版”默认延续当前任务。明确新主题时建立新任务；对象无法确定时保留任务并询问具体缺项。草稿确认与实际发布分开，刷新或重启恢复任务不会重发公告。

复用偏好如“通知简洁、面向营业员”可经审核长期保存；某一天的公告正文作为任务和原始证据保存，不自动泛化成永久经营规则。

### 已确认经营规则

优先接入以下已在本次会话中明确的规则，并建立可重读的正式来源：

- 门店普通付款使用现金库或信号机微信；老板发红包使用老板微信，作为有明确范围的例外。
- 先按笔数和金额汇总核对，差异给老板具体原因；汇总一致不等于已证明单笔红包业务真实。
- 流水完整号、尾号及已录入记录要区分；证据关联不能产生重复收付款。
- 酬金时效从2026年11月1日开始，比较外部业务完成时间与本系统提交时间，绝对差超过180秒影响该笔营业员酬金，对账仍继续。银行时间不能冒充外部完成时间。

规则条目分别记录适用门店、角色、有效日期、例外、确认来源和实现状态。聊天指令与代码现状不一致时显示差异，不能用记忆覆盖账务处理器或自动宣布规则已上线。

## 来源版本与权限契约

建议为来源制定稳定ID，以下均是待实现的ERP约定，不是上游已经登记的能力：`erp.knowledge`、`erp.reviewed-teaching`、`erp.accounting-policy`。任务记录另由ERP管理。

- 完整版本由正文、适用范围、有效日期、启停状态及相关授权版本的规范化摘要组成，不能只固定写v1。
- 上游摘录采用Unicode code points范围，必须与可重读原文逐字一致。
- tenant映射经营组织，project区分阿里云与原coze项目；branch和用户归属继续由来源授权检查。scope只分类，不能充当权限隔离。
- 员工可提交纠错；是否可提案、审核、修订按现有职责映射。不得让模型代替老板签发审核身份。
- 不能只用一个老板级通用Token替所有员工检索；服务身份必须对应当前被授权主体，或采用明确支持代理身份且已验证的受信机制。
- 两个进销存默认隔离；共用规则需显式发布到各自项目，不能直接复制另一个项目的凭证或本机测试profile。

跨库同步不天然具备最终一致性保证。来源/权限可采用记忆库中的受控快照，但消费者使用前必须与ERP当前版本及权限重新比对；不一致或无法核验就阻断该知识。原业务提交时再次授权和检查版本。标准服务的事务锁只保护其适配器所连接的权威数据，不证明远端ERP在整段调用中没有变化。此项须经接口与故障验收后才可宣称接通，不能宣称跨库原子提交。

## 同步与故障处理

复用ERP事务事件，在同一事务中保存需要同步的稳定来源版本和任务。新增独立的记忆投递表/投递状态，不能抢占现有网页通知消费者的pending/sent状态。

投递保存目标项目、来源ID、来源版本、操作类型、稳定commandId、完整原请求、状态与回执。相同事件不重复提案；结果未知先查原回执。dispatch结果不明时查原凭证status，不另建凭证重发。业务交易不能等待记忆服务HTTP响应后才提交。

停用或改版事件优先同步；同步完成前，ERP消费端用当前来源版本阻断旧知识。记忆服务故障时保留任务和本地确定性业务功能，明确提示记忆不可用；需要新规则依据而无法核验的请求转人工，不套用旧缓存。

## 实施任务与完成条件

以下为拟新增模块，尚未编写或部署。

| 顺序 | 改动位置 | 可观察完成条件 |
| --- | --- | --- |
| 1 | 服务端任务存储、`assistant-chat.js`与`assistant-context.js` | 完整HTTP入口连续多轮、刷新、重启后恢复正确对象；换题和换账号不串任务 |
| 2 | 独立记忆服务的ERP标准项目模块与业务策略 | capabilities声明正确namespace、来源、消费者与检索能力；不是demo身份 |
| 3 | `employee-knowledge.js`、`assistant-feedback.js`及独立投递工作者 | 审核后入候选，重复事件不重复；“已处理”不会误当“已生效” |
| 4 | ERP记忆网关、工作助理入口、数字大脑查询入口 | 改写问法可找到正确依据，实时金额仍从原单查询；错误原因可见 |
| 5 | 记忆管理页面 | 老板能查看来源、条件、版本、审核状态、有效日期，修订或停用 |
| 6 | 来源失效、权限撤销、故障恢复及回退测试 | 旧知识、未审核知识、其他项目数据不能用于当前任务；故障不导致重复业务 |

向量检索在最小场景闭环后再启用。上游当前是精确扫描，冷缓存构建和范围过大可能增加耗时；没有现成的大规模索引性能保证。先限定场景、后台预热已审核资料、按任务限制上下文字节预算，再测冷/热缓存与并发耗时。阈值用真实中文改写问题校准，不能照抄示例数值作为效果保证。

## 验收与回退

- 跨天恢复“修改电子屏”任务，保留目标ID、版本和要求，不自动发布。
- 用不同说法问付款方式，能解释现金库/信号机微信与老板红包例外。
- 10月与11月分别问3分钟规则，日期和时间依据正确；缺外部时间时不给出虚假资格结论。
- 规则改版、停用、来源撤权后旧版本不再使用，原历史可追溯。
- 员工、老板、顾客及两个项目身份实际隔离；不能只换请求JSON里的projectId进行“验证”。
- 重复事件、超时、响应丢失和服务重启不会重复提案、发公告或产生收付款。
- 无embedding时只报告关键词模式；模拟通过不能写成真实语义检索通过。
- 关闭采集与记忆读取的配置开关，保留原知识库、账务处理器及任务记录。回退不删除原业务数据。

# 全国多门店容量改造方案（2026-10-09）

## 目标与现状

目标按 300 家门店、每店约 100 名员工（合计约 3 万名员工）、每日数万台终端设计。以每日 3 万笔销售为容量测试基线，一年约 1095 万笔销售主单，明细、资金和库存流水会更多；若每名员工每天签到和签退各一次，最多约 6 万条出勤事件/日。这是设计负载，不是当前系统已达到的容量。

当前系统是单账套、单进程 Node 服务。业务集合保存在一份 SQLite 数据库中，但每次事务会读取整个账套，并删除、重写所有集合。所有门店共享一组内存数据结构，没有租户、门店字段和数据库级隔离。这个实现适合目前试用，不能支撑全国多门店并发。隔离内存库的基准：1000 张简化销售单写入约 4 ms；10000 张约 37 ms，读取约 16 ms。真实单据更大，单进程同步重写会阻塞其他请求。基准只用于证明增长趋势，不是生产压测。

## 必须完成的底层改造

1. **组织和权限**：建立 tenant（企业）、branch（门店）、warehouse（仓库）层级。每一张业务单、流水、操作记录都带 tenant_id 和 branch_id。权限按总部、区域、门店、岗位和本人分层；人员可被授权多店，调岗和离职应立即撤销访问；每次读写在数据库层加范围条件。老板可按授权范围看全公司，员工只看授权门店与本人业务。跨租户查询必须拒绝。
2. **数据库**：迁到 PostgreSQL。销售主单、明细、库存串码、资金流水、接待、出勤分别建表；统一主键、业务短单号、外键、唯一约束和必要索引。历史大表按业务日期分区，避免单次写入扫描整账。迁移需要双写比对和可回退窗口。
3. **账货钱强一致**：销售、退货、采购验收、收款确认在同一数据库事务里更新对应台账；串码全局唯一，库存不可负，收款不可重复确认。财务采用追加式流水和红冲，禁止覆盖历史；用幂等键防止重复提交。
4. **异步任务**：通知、报表汇总、外部同步改用可靠消息队列与 outbox。开单交易提交后即返回，不等通知发送。失败任务可重试并可追踪；单据状态以数据库提交为准。
5. **查询和数字助理**：建立按门店、日期、品类汇总的只读查询模型。助理只调用权限受控的查询接口，展示统计口径、更新时间和可追溯单据；不能让模型直接写 SQL、改金额或跨门店读取。复杂问题若无可信数据，明确答“无法核实”。
6. **运维**：多实例无状态应用、连接池、限流、监控、审计、自动备份、定期恢复演练。图片和附件进对象存储，数据库仅保存索引和校验信息。

## 验收基线

- 构造至少 300 门店、约 3 万员工账号、连续 12 个月不少于 1000 万销售单及相应明细、库存和资金流水的测试数据；同时生成约 6 万条/日签到签退事件，测试跨店调岗、离职停用和区域授权。
- 单独压测 3 万有效登录会话、集中签到、总部跨 300 店统计及员工本人查询，验证权限缓存失效、会话回收和人员批量导入。
- 模拟正常与高峰混合业务；指标建议先以峰值 200 次写入/秒、1000 次查询/秒为压测目标，正式数值须依据门店实际流量调整。记录 p95/p99 延迟、错误率和数据库锁等待，不以单个平均值替代。
- 对每张单做账货钱守恒校验；并发扫描同一串码只允许一笔成功；重复请求不得重复扣库或收款。销售、退货和红冲都应留下操作员、时间、来源和审批轨迹。
- 测试总部查全公司、区域查辖区、店长查本店、店员查本人，并覆盖越权 URL、智能搜索和助理问答。
- 故障演练覆盖进程重启、队列失败、数据库主从切换和从备份恢复；设定并验证恢复点与恢复时间目标。

## 当前交付边界

现已上线的个人数字助理是单店账套的首版：能按账号权限查询已录入数据、打开相关页面、形成待确认开单草稿、登记签到签退和向老板提交待核实情况。它没有通用模型推理，也没有 300 门店容量保证。全国版须按上述顺序完成底层迁移，再做大规模压测和上线。

## 设计依据

- PostgreSQL 分区表的主键/唯一约束必须包含分区键，且需提前建立覆盖目标日期的分区：https://www.postgresql.org/docs/current/ddl-partitioning.html
- 行级安全策略用于租户范围的二次防护；生产运行角色不得具有 BYPASSRLS，且每个事务须设置租户上下文：https://www.postgresql.org/docs/current/ddl-rowsecurity.html
- 备份与持续 WAL 归档支持按时间点恢复；是否达到恢复目标须通过演练验证：https://www.postgresql.org/docs/current/continuous-archiving.html

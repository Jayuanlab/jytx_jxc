## 1. 规则的使用与优先级

### 本次复核记录（2026-10-22）

- 门店普通付款与老板红包适用范围已分开：红包仅允许老板本人微信，不使用信号机微信，重试不重复记账。
- 修正机器字段：商品预设售价使用现行`salePrice`；退款及冲正资金通过`receipts.originalReceiptId`关联原资金流水；规则版本来自模型顶层，未落库的批次字段不标为已上线。
- 外部流水号若已损失数字精度，停止自动认可并要求重导文本；完整号显式标记为full时，保留开头的X。
- 禁用网络及大模型接口后，24项既有业务测试和10项红包专项检查通过；另有销售库存链路、模型结构/身份匹配、助理本地模型回答及浏览器账户选项验证通过。
- 两条历史仓库测试期望已与现行规则核对：摄像头属于配件仓；商品编码自动生成，建档不指定实际入库位置，C仓名称不追加YD。仅修正测试，未据旧期望改线上仓库规则。
- 证据自动认可写回和全流程账务编排仍是待接入能力。现有日常办理入口、精确核算、汇总比对、库存与微信余额核对不依赖大模型；服务器及业务数据库仍须正常可用。

按事实所属领域分别采用依据：移动原流水证明移动办理或平台余额事件，银行原流水证明银行收付，销售原单证明成交约定，实物验收证明货物状态。不得用一张银行流水改变商品数量或原成交价格。

用户本次明确确认的经营规则优先于旧说明和旧示例。金额守恒、原单有效、门店隔离和实际办理权限由服务端继续检查。未知手续费、成本、税率和政策条件保留待核，不由模型猜测。

本版每条规则实际包含：`id,model,name,condition,effect,implementation,handlers`；版本和依据在模型顶层统一定义。本版21条规则已经列入机器定义。现有业务审计沿用原处理器；统一处理批次记录规则版本属于后续accountingRuns集成，不能把目标字段当作已经全部落库。

## 2. 汇总比对决策表

| 解析状态 | 两边有效笔数 | 金额合计 | 结论与后续 |
| --- | --- | --- | --- |
| 有读取错误 | 任意 | 任意 | 数据待修正，显示原行，不能保存为一致 |
| 任一侧无有效交易 | 0或空 | 任意 | 检查期间、方向及金额列；不能把两边空文件算通过 |
| 无错误 | 一致 | 一致 | 汇总通过，可直接保存；不要求逐笔人工处理 |
| 无错误 | 不一致 | 一致 | 笔数差异，必要时查合并、分笔或漏项 |
| 无错误 | 一致 | 不一致 | 金额差异，展开明细核查 |
| 无错误 | 不一致 | 不一致 | 列出两项差额，先查筛选范围和列映射 |

合计行、空白行和筛选排除行分别记录。汇总口径使用选定的期间、方向及绝对金额/带符号金额方式，保存后重查不变。

## 3. 真实流水认可决策表

| 原填写与外部证据 | 日期/金额/业务域及必要方向 | 候选关系 | 结果 |
| --- | --- | --- | --- |
| 完整号一致 | 相符 | 双向唯一 | 按完整号认可 |
| 原填写为尾号，外部有完整号 | 相符 | 双向唯一 | 按尾号定位认可，保留两个编号 |
| 编号有笔误或缺失 | 相符 | 双向唯一 | 按唯一真实事实认可，记录原因 |
| 尾号相同的两条完整号不同 | 相符 | 多候选 | 待查，不合并两条真实流水 |
| 编号相同 | 金额不符或日期冲突 | 任意 | 列差异，不因编号相同认可金额 |
| 同日同额多笔 | 相符 | 不能唯一定位 | 待查，不能按列表先后顺序强配 |
| 两条外部流水争用一个内部记录 | 相符 | 反向不唯一 | 待查，不能重复认可 |
| 原完整号已被独立核实且与外部完整号冲突 | 其他事实相符 | 任意 | 冲突待查；不能把已核实号随意解释成笔误 |
| 原单已红冲或原事实变化 | 任意 | 任意 | 原认可失效，走原更正和重算 |

“双向唯一”指：该原行只对应一个有效内部候选，同时这个内部候选没有被其他外部原行争用。不能只看尾号在一侧唯一。

## 4. 认可样例

### 原来只填了尾5位

```text
营业员原填写：00012
内部原单：2026-10-22、付款30元、银行经营账户
银行导出：20261022009900012、2026-10-22、支出30元
同业务域、同日期、同金额且双向唯一

结果：认可真实流水对应；记录方法suffix。
保留：原填写00012、外部完整号20261022009900012、原文件哈希和原行号。
资金：仍沿用原付款receiptId，不再新增−30元。
```

### 填写有误，但事实唯一

```text
营业员原填写：手填错号A
原单：当天支出86.50元
银行导出：当天唯一一笔同业务域支出86.50元
原单未被红冲，双方没有其他候选

结果：以真实外部证据认可对应，方法unique_facts；原错号留痕。
如果当天有两笔86.50元，则转待查。
```

### 汇总一致，逐笔金额不相同

```text
移动：2笔，10.10元和20.20元，总计30.30元。
银行：2笔，5.00元和25.30元，总计30.30元。

结果：本次笔数金额汇总通过，符合老板的快速核对规则。
逐笔认可：没有足够唯一证据时仍不标记逐笔认可。
两种结果分开显示，不把“汇总通过”扩成“每一笔都已证实相同”。
```

## 5. 账务和流程验收

| 场景 | 必须观察到的结果 |
| --- | --- |
| 信号机微信付款30元 | 只产生或沿用原30元付款，进入该账户减少；聚合支付不混计 |
| 30元换现两张原单 | 建立关联；收付款流水数量和原金额不因关联变化 |
| 首次观察余额280.13 | 保存观察依据或营业员实看；不自动生成+280.13元转入 |
| 下一日余额核对 | 按上次已核余额及此后实际增减算应有，实看差额单列 |
| 银行流水对应已有付款 | 保存证据关联或合法核实状态；不重复支出 |
| 订货已付未收货 | 资金和预付有记录，可售库存不增加 |
| 分批验收入库 | 只增加实际收到的商品与串号；剩余待收继续挂单 |
| 调拨 | 数量和成本在两仓守恒，不确认销售收入 |
| 服务项目销售 | 使用真实服务商品；不产生不存在的实物库存 |
| 退货及退款 | 关联原销售、原明细和原收款；实际退款与成交冲减分开 |
| 原单已红冲 | 旧认可标记失效，原单与冲正痕迹同时可查 |
| 原日结已锁定 | 新证据不会悄悄改历史快照；按原更正流程处理 |
| 重复请求或网络重试 | 返回原办理结果，不增加第二份业务或资金流水 |
| 没有大模型 | 原文件解析、精确计算、规则识别和差异查询继续工作 |
| 越权员工/顾客模式 | 不取得未经授权的原银行文件、成本、工资或办理权限 |

## 6. 异常处理闭环

发现异常 → 保存原单与证据 → 明确责任人 → 查清实际原因 → 补证或调用原业务更正 → 重新核算 → 保存解决依据。

每个异常保留原值、预期值、差额、规则ID、来源、责任人和处理轨迹。已确认实点、实付或收货的人不能被数字大脑虚构；系统自动认可使用自己的办理身份。

## 7. 可执行模型验证

身份匹配参考实现位于`server/src/statement-identities.js`，其输入输出都是纯数据，不写账、不改库存。模型验收脚本检查十类模型、实体关联、规则编号、命名空间、尾号和唯一事实匹配、争用与冲突。

运行：

```powershell
node tools/validate-accounting-model-20261022.cjs
```

现有汇总比对另有`server/test/statement-comparisons.test.js`及隔离HTTP/浏览器测试，覆盖笔数和金额、Excel/CSV、日期、重复保存、历史记录、原文件下载和权限。

通过参考实现验收，表示模型决策可以执行；仍需在写回接口集成中验证事务、门店权限、原文件保存、原单变化及回滚，才能将相应能力标记为线上可用。
